# Actionable Handoff — v1.3.1

本文件是用户交接的唯一详细规范；各角色只引用。授权边界与默认放行范围统一引用 `authorization.md`，交接时在同一代码块或摘要中直接写明适用范围与停止点，不要求用户拼接多份规则文件。

**面向人的最小充分信息原则（本文件为唯一权威，各角色只引用）：** AI 主动筛选复杂度，只向用户呈现理解真实状态与边界、判断重大风险与取舍、以及采取下一步行动所必需的信息；不要求用户筛选技术流水账或逐条确认常规前提。
- **正常回复结构：** 先给当前真实结论与状态边界，再给唯一明确的下一步或用户待办；确有重大产品、科研、架构取舍或超范围授权需求时，才在文末集中列问题、推荐、关键取舍与用户要回答什么。没有人工决策时不生成决策清单；没有下一步时不强行填固定模板。回复深度由决策意义决定，不硬套固定三段顺序或每步三行结尾。
- **自动过滤与按需溯源：** 工具面板已展示的常规状态行、已解决的 `REWORK` 历史、普通技术参数、常规 `Assumptions`、内部哈希与 `loopId` 默认不堆砌在主回复中也不请求确认；用户主动追问技术细节或审计材料时，按原合同与证据精确提供并标出位置。
- **异常与边界不可被精简掩盖：** 遇到 `HUMAN_REQUIRED`、审查未完成或状态不可信、权限缺口、多个独立阻断同时生效时，必须在主回复中明确不能继续、真实原因、活跃阻断及可执行处理选项（不依赖用户展开工具面板才看到），不得为缩短回复漏报阻断或错报 `PASS`/`READY`。
- **状态与授权准确区分：** Design `PASS`、Code 本地 `PASS`、PR bot `READY`、CI 通过、人工验收与 `merge` 各自独立，不得互相替代。进入已授权阶段后，本任务范围内的常规修改、验证、`commit` 与 `push` 按 `authorization.md` 自动完成，不再逐项请示。

**切换另一个对话或 Worker 时**，优先一个可用的完整包或精确可访问引用，明确：
- **去哪里：** 继续当前 Worker / 新建独立 Reviewer 对话（写清选哪个）。
- **带什么：** 文件包名称及实际下载链接，或准确引用；需要时写“下载 → 新建对话 → 上传”，不让用户自行从多个报告拼材料。
- **发什么：** 已准备好的完整可复制 Prompt，不要求用户自行撰写。
- **回来什么：** 对方应返回的结论/文件，以及把结果交回哪里。

**单次使用的 Worker / Reviewer / 修复 Prompt 默认直接在回复里提供一个完整、可复制的代码块，不为 Prompt 单独生成下载文件，也不把启动 Prompt 藏进 ZIP。** 仅当材料需要反复使用、长期留存、跨会话迁移、逐字节核验或包含实际附件/多文件证据时，才提供可下载文件或准确、可访问的固定引用；一个文件即可交接时不强行打包 ZIP。**如文件未实际生成或无法验证链接，不得假称可下载；**改给自包含文本或明确缺口。若冻结合同已满足实施前提，就明确写“下一步可开始代码开发”，并提供已授权范围内的 Worker Prompt；仍有关卡阻塞则明确不可开发。正式 Worker Prompt 前可有一句用户操作提示，Prompt 本身仍保持一个完整代码块。

**主控对话续接：** 在阶段已完成、准备进入独立新任务，或长对话开始造成上下文/版本混淆时，Lead 主动建议是否新开主控对话；正常讨论或同任务返工继续原对话，不按固定字数强制切换，也不声称能精确检测剩余上下文容量。建议切换时明确理由与下一步，给可核实的既有合同/状态引用或必要的单份续接文件，以及直接可复制的启动 Prompt。**换对话不等于开新任务**：同一任务保留原 `policy_sha`、冻结合同、ReviewLoop/PR 状态与权限；只有真正新任务才用当时的 `reviewloop spec` 另定 `policy_sha`。新对话须先核实当前可信状态，不得把旧快照当作新的执行许可。

**用户手动交接以 1 次为目标，2 次通常可接受。** 不因此减少必要独立审查、绕过强制关卡或预先宣称自动委派成功；超过时说明具体阻塞和为何不能复用现有工具。四角色正文只作简短引用。
- **决定来源：** 代发评论、转贴审查与 AI 建议的归属标注统一遵循 `authorization.md` §5，本文件不另行定义。
