# Engineering Task Spec — v1.3.1

本规范继承原 v11.5 的单任务规格、阶段、验收与证据义务；项目统筹、设计、独立审查由相邻 Skill 承担。已冻结任务仍按其原合同审查，不追改验收边界。

## 职责（Code 阶段，与写 Work Contract 时的标准）
1. **写 Work Contract 时**（Design 文件最后一节）：按本规范的标准，把已收敛目标和设计约束写成自包含、可执行、可验收的合同。
2. **启动 Code 时**：把**已通过审查的设计**原样交给 Worker，不再另编一份。不是路线图设计师、独立审查人或 ReviewLoop 控制器。

## 启动 Code 的前提
用户已明确说“Code”，且满足 `authorization.md` 的阶段前提。Worker 需要：
- 该任务的 `policy_sha`、完整已批准设计文件和它的 `designSha256`（取自 Design PASS）；
- 适用授权边界（见 `authorization.md` 及显式收紧/例外）、需要的审查路径、实际仓库基线。

**设计原文必须逐字交给 `reviewloop_begin(taskType: "code")` 的合同，并带上 `designSha256`。** 内容与 `designSha256` 对不上，说明它不是通过审查的那一份：停止，取得新的 Design PASS，不得手工改写后继续。没有 Design PASS 的任务不得启动 Code；只有 Brief、五句话或改写过的摘要不算设计。关键架构问题仍未解决则回 Design/主控，不能用“实现时决定”掩盖。

## Work Contract 的写法
- 写可观察的结果、现有机制、必需不变量和边界，不替 Worker 决定无关函数/文件/内部数据结构。
- 必要约束和既定决定直接写进合同；只给链接而不带操作约束不算自包含。保留上游版本与来源，摘录不是第二套可自行改写的合同。
- 写少量全局 AC。每项重要 AC 对应“声明 → 可能失败 → 足够证据”；规定不能发生什么，而非只写“增加测试”。必需证据和可选增强检查在开工前分清。
- 简单任务只设一个完成门槛。有独立依赖或恢复价值才分阶段，通常两三阶段。每阶段有稳定 ID、目标/边界、退出条件、证据、带入下阶段的不变量。中间阶段不验未来功能；全部阶段通过后仍做全合同集成验证。
- 先做非破坏性 preflight：工作区已有改动、实际基线、已有失败、检查入口、数据/fixture 与权限。已验证命令才写成事实；未验证命令让 Worker 查明。若与冻结假设实质冲突或必需证据不可取得，停止相关实施并精确报阻塞。

## 证据的最低要求
按主张选证据，不机械使用通用大清单：
- 集成：真实调用链和代表性既有消费者；UI 接线需要运行交互或端到端检查，不能只用 view-model 测试。
- 持久化/迁移：写入或迁移后 reload/restart 检查；旧数据/关联应实际仍在。
- 故障/重试/并发：到达所声称阶段的故障注入或交错；断言目标阶段和副作用，不能被更早 guard 拦截后误报通过。
- 导出/删除：回读导出内容；检查持久化删除及下游状态，不只检查界面或文件存在。
- 科研：已知答案、物理/数值不变量、适用容差、缺失/NaN/常量等边界；按需真实数据和独立可信参考。分别验证数量、单位、处理方法与显示映射；截图和软件测试 PASS 不能替代科学有效性。无参考时明确未证实的主张。

## 执行和现有工具交接
遵循现场已安装且适用的 Worker Policy（ReviewLoop `agent-policy/COMMON.md`），不在这里复制其控制器、API 或 PR bot 协议。完整合同、阶段顺序、全局约束和必需证据必须无损传递。

如使用冻结检查计划的工具，全局检查须能在每个阶段运行；阶段检查绑定本阶段；最终专用检查有实际执行与提交证据路径。必需运行/文件/人工证据必须进入工具支持的强制证据机制，不能只写说明文字。新测试/配置需要改变冻结检查入口时在大规模编辑前解决，不能暗改或禁用关卡；工具无法表达时明确说明人工路径或阻塞，不杜撰 API。

一个授权任务的阶段与普通修复在同一任务中继续，不逐次请求用户许可；保持合同和证据连续性。Code 阶段的默认放行边界（任务范围内修改、验证、正常 `commit`/`push` 至专属分支及 PR 交接更新）、外部副作用核查与高影响停止点（`merge`、部署、权限变更、`HUMAN_REQUIRED` 等）统一遵循 `authorization.md`，不在本文件重复定义。保护原始数据、现有他人编辑、测试和无关行为，不为变绿弱化验证。

Worker 完成后交付：任务/合同版本、base/head、PR 或可检查差异、AC 对应证据、真实的审查结果、未验证项以及必要用户验收步骤。PR bot 当前 HEAD 的 `READY`、CI、用户验收与合并各自独立判定；不能以 Worker 自述替代独立验收。

## 输出
按 `handoff.md`，在代码块前仅用一句说明下一步如何交给 Worker（区分已授权执行与仅供审阅）；其后只给一个可一次复制的完整外层代码块，内部包含：
Goal；任务 ID、`policy_sha`、`designSha256`；设计文件位置（PR 中的确切版本）；授权边界（引用 `authorization.md` 及显式收紧/例外）；停止点；执行/审查与交付。**设计正文本身不重复粘贴改写**，Worker 按位置读取同一份已批准文件。

省略无用章节；内部示例用更长外层 fence，保持一次复制。代码块后不追加讲解。未解决重大问题时，不输出可执行指令；明确阻塞、下一步具体操作与文末需要用户决定的取舍。
